# V0.2 — BOSS 登录连接（Raw CDP）

状态：

**已完成 / 已冻结**

Git Tag：

```text
v0.2.0
```

目标：

> 让 JobPilot 可以建立并持久保存由用户本人完成的 BOSS 登录 Session。

范围：

* 真实 Google Chrome + 独立持久化 Profile
* Raw CDP Browser Driver（ChromeCDPManager / RawCDPClient）
* BOSS 独立 persistent Browser Profile
* TEST / PRODUCTION Browser Profile 隔离
* 打开可视化 BOSS 登录页面
* 用户手动完成扫码 / 短信 / CAPTCHA
* 只读登录状态检查（不导航 / 不创建页面）
* Browser Profile 持久保存登录信息
* 平台连接状态管理
* 检查连接
* 重新连接
* 断开连接
* 清理 JobPilot 管理的 BOSS Profile
* Electron IPC 接入
* Windows 打包后的兼容性验证

明确不包含：

* 岗位搜索
* 岗位列表解析
* JD 解析
* AI 岗位评分
* 自动投递
* HR 消息读取
* 自动发送消息
* CAPTCHA 或安全机制绕过
* 反检测 / stealth

验收链路：

```text
连接 BOSS
↓
用户手动登录
↓
JobPilot 确认连接
↓
关闭 JobPilot
↓
重新启动
↓
Browser Profile 仍然存在
↓
Session 可以继续使用
↓
可以检查当前连接
↓
断开连接后清除 JobPilot 管理的认证数据
```

# V0.4 — AI 岗位匹配

状态：

**V0.4-A 已完成并提交，V0.4-B 开发完成（等待人工验收），V0.4-C 计划中**

目标：

> 判断已经发现的岗位到底是否值得投递。

## V0.4-A — Candidate Profile / 简历基础能力（已完成）

状态：

**已完成并提交（V0.4-A checkpoint）**

已完成：

* 简历上传 / 查看 / 更换 / 移除（PDF / DOCX，本地解析，不依赖第三方服务）
* 版面结构解析（V0.4-A 解析架构调整）：PDF 先还原「内容块 + 视觉顺序」，再按 Section 语义识别，
  不依赖固定模板 / 固定左右布局 / 固定栏目名（教育背景/学历信息、实习经历/职业经历、专业技能/技术能力等同义标题均可识别）
* 简历纯文本本地提取（PDF：pdfjs 版面行重建，保留行内字段间隔；DOCX：mammoth 段落序列）
* 规则解析器：姓名 / 电话 / 邮箱 / 工作年限 / 教育背景 / 工作与实习经历 / 项目经历 / 技能 / 证书 / 语言能力 / 自我评价
* 解析只提取简历原文，不编造简历中不存在的信息；结构化字段与原文保持对应关系
* 教育经历：多段分别解析、多行版式（学校/时间/专业/学历分行）合并、tab 字段行（学校|专业|学历|时间）识别、无法确定留空
* 工作 / 实习经历：每段独立记录（时间在左 / 在右、公司+右侧时间、多行条目标题均支持），公司 / 职位 / 时间 / 内容对应，内容不串段
* 技能解析：从技能描述中识别技术实体 / 能力短语（Python、Pytest、Selenium、Java、Java单元测试、PO模式、CI/CD、Docker…），
  过滤序号 / 连接词 / 描述性动词 / 被拆开的 CI/CD / 无独立意义的普通词
* 解析完整性提示（warnings）：检测到某部分但未识别完整时提示用户手动补充，用户确认后清空
* 「我的资料」页面：当前简历状态、候选人资料只读视图、可编辑修正、保存确认、解析不完整提示
* 更换简历明确提示会重新生成候选人资料；资料过期时明确提示并需用户确认后重新解析
* 原始简历与结构化资料均持久化（SQLite，userData 目录），TEST / PRODUCTION 隔离
* 自动测试：解析器多样式回归（单栏/双栏阅读顺序/时间左右/多段教育实习/技能列表/自然语言段落/不同栏目名）+
  全链路持久化测试 + 用户真实简历 PDF 端到端回归

## V0.4-B — AI 岗位决策引擎（单岗位，开发完成）

状态：

**开发完成，等待人工验收**

已完成：

* 求职规则设置（Settings「求职规则」）：目标岗位方向 / 接受城市 / 最低薪资 / 是否接受外包 / 单双休 /
  学历与经验容忍度 / 明确排除关键词；用户的明确规则优先级高于引擎判断
* 本地可解释岗位决策引擎（core/decision，纯函数、确定性、可测试；预留后续替换为 LLM Provider）：
  - 只使用 确认后的 Candidate Profile + 求职规则 + 岗位完整 JD，不调用外部服务
  - 硬规则违反 → SKIP（城市 / 薪资 / 外包 / 单休 / 学历与经验严格模式 / 排除词）
  - 明显符合 → AUTO_APPLY；存在关键风险 / 不确定 → REVIEW（不确定时宁可 REVIEW，不擅自 AUTO_APPLY / SKIP）
  - 「简历没写」≠「用户不会」：JD 要求但资料未体现 → 进入 REVIEW 而非臆断
  - 决策理由为模板化短句：主要匹配点 / 主要风险 / 关键不确定项 / 简短决策理由（可展开查看）
  - 内部匹配分与置信度仅作参考，不是产品核心
* 决策结果持久化：同一岗位复用已有结果；支持主动重新分析；
  Candidate Profile / 求职规则 / JD 变化后旧结果明确标记过期并给出具体原因
* Jobs 工作台详情区「JobPilot 决策」模块：单岗位分析，不做批量
* 自动测试：决策引擎三类验收场景（AUTO_APPLY / SKIP / REVIEW + 防编造）+ 持久化 / 复用 / 过期测试

明确不包含（V0.4-C 再实现）：

* 批量自动决策全部 NEW 岗位
* 自动投递 / 自动联系 HR
* 自动修改简历

预计能力（V0.4-C）：

* 批量岗位决策
* 决策列表视图
* 硬规则过滤
* 本地保存匹配结果

重要原则：

用户明确设置的硬条件优先级高于 AI 判断。

例如：

```text
最低薪资
排除销售
排除行业
城市
单双休
外包偏好
```

AI 不只输出：

```text
87分
```

还必须解释：

> 为什么值得投 / 为什么不建议投。

# V0.5 — 投递流程

状态：

**方向规划**

目标：

> 从岗位推荐逐渐进入可控的投递执行。

应循序渐进：

```text
AI推荐
↓
用户确认
↓
辅助投递
↓
TEST 模拟
↓
受控自动化
```

禁止一开始直接实现无限制批量投递。

最终需要考虑：

* 每日投递上限
* 平台异常 / 风控信号
* 人工接管
* TEST / PRODUCTION
* 投递日志
* 防止重复投递

# 后续 — 求职反馈优化

长期目标：

让 JobPilot 根据真实求职结果辅助优化策略。

例如：

```text
投递
↓
HR回复
↓
沟通
↓
面试
↓
Offer
```

结合这些真实结果分析：

* 哪类岗位回复率更高
* 哪种薪资区间更容易获得沟通
* 哪些岗位方向更适合用户
* 哪些搜索策略效率低

系统可以提出：

```text
提高某类岗位权重
降低某类岗位权重
调整搜索范围
调整投递策略
```

但最终策略修改权仍然属于用户。

# 版本发布纪律

每一个版本按照：

```text
开发
↓
定向测试
↓
回归检查
↓
Lint
↓
TypeCheck
↓
Build
↓
Dist
↓
必要的人工验收
↓
Commit
↓
稳定版本按需创建 Tag
```

不要因为下一版本“看起来很简单”，就在当前任务中顺手实现。

宁可：

> 小版本完整、稳定、可验收

也不要：

> 大版本功能很多但只有一半可靠。
