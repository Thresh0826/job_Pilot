# V0.2 — BOSS 登录连接（Raw CDP）

状态：

**开发中（技术路线已定：真实 Chrome + Raw CDP）**

目标：

> 让 JobPilot 可以建立并持久保存由用户本人完成的 BOSS 登录 Session。

范围：

* 真实 Google Chrome + 独立持久化 Profile
* Raw CDP Browser Driver（ChromeCDPManager / RawCDPClient）
* BOSS 独立 persistent Browser Profile
* TEST / PRODUCTION Browser Profile 隔离
* 打开可视化 BOSS 登录页面
* 用户手动完成扫码 / 短信 / CAPTCHA
* 只读登录状态检查（不导航 / 不创建页面）
* Browser Profile 持久保存登录信息
* 平台连接状态管理
* 检查连接
* 重新连接
* 断开连接
* 清理 JobPilot 管理的 BOSS Profile
* Electron IPC 接入
* Windows 打包后的兼容性验证

明确不包含：

* 岗位搜索
* 岗位列表解析
* JD 解析
* AI 岗位评分
* 自动投递
* HR 消息读取
* 自动发送消息
* CAPTCHA 或安全机制绕过
* 反检测 / stealth

验收链路：

```text
连接 BOSS
↓
用户手动登录
↓
JobPilot 确认连接
↓
关闭 JobPilot
↓
重新启动
↓
Browser Profile 仍然存在
↓
Session 可以继续使用
↓
可以检查当前连接
↓
断开连接后清除 JobPilot 管理的认证数据
```

# V0.3 — BOSS 岗位发现

状态：

**计划中**

目标：

> 让 JobPilot 可以从 BOSS 获取岗位信息，但暂时不执行投递。

预计范围：

* 根据用户设置执行岗位搜索
* 读取岗位列表
* 打开并读取岗位详情
* JD 内容提取
* 将 BOSS 数据转换成 JobPilot 统一 Job Model
* 必要的翻页 / 滚动
* 去重
* 本地保存已发现岗位
* 区分新岗位 / 已查看岗位
* 页面异常和结构变化处理

初期验证阶段优先使用 TEST 模式。

明确不包含：

* 自动投递
* 自动发送 HR 消息
* 安全机制绕过

如果此阶段的数据抓取还不稳定：

AI 岗位评分继续留在 V0.4。

# V0.4 — AI 岗位匹配

状态：

**计划中**

目标：

> 判断已经发现的岗位到底是否值得投递。

预计能力：

* 读取用户资料
* 读取求职策略
* 分析标准化 JD
* 硬规则过滤
* AI 匹配评分
* 推荐原因
* 风险 / 不匹配原因
* 匹配阈值
* 本地保存匹配结果

重要原则：

用户明确设置的硬条件优先级高于 AI 判断。

例如：

```text
最低薪资
排除销售
排除行业
城市
单双休
外包偏好
```

AI 不只输出：

```text
87分
```

还必须解释：

> 为什么值得投 / 为什么不建议投。

# V0.5 — 投递流程

状态：

**方向规划**

目标：

> 从岗位推荐逐渐进入可控的投递执行。

应循序渐进：

```text
AI推荐
↓
用户确认
↓
辅助投递
↓
TEST 模拟
↓
受控自动化
```

禁止一开始直接实现无限制批量投递。

最终需要考虑：

* 每日投递上限
* 平台异常 / 风控信号
* 人工接管
* TEST / PRODUCTION
* 投递日志
* 防止重复投递

# V0.6 — 招聘沟通读取

状态：

**方向规划**

预计方向：

* 获取 HR 对话
* 标准化消息数据
* 检测新消息
* 检测未读
* 判断重要事件
* 通知用户
* 在 JobPilot 内展示沟通记录

此阶段优先保证：

**能可靠读取和理解消息。**

在消息分类和权限控制可靠之前，不自动发送 AI 回复。

# V0.7 — AI 沟通助手

状态：

**方向规划**

预计能力：

* 判断 HR 意图
* 生成回复建议
* 使用真实简历和用户资料
* 遵守 AI 权限

* 学历

# 后续 — 求职反馈优化

长期目标：

让 JobPilot 根据真实求职结果辅助优化策略。

例如：

```text
投递
↓
HR回复
↓
沟通
↓
面试
↓
Offer
```

结合这些真实结果分析：

* 哪类岗位回复率更高
* 哪种薪资区间更容易获得沟通
* 哪些岗位方向更适合用户
* 哪些搜索策略效率低

系统可以提出：

```text
提高某类岗位权重
降低某类岗位权重
调整搜索范围
调整投递策略
```

但最终策略修改权仍然属于用户。

# 版本发布纪律

每一个版本按照：

```text
开发
↓
定向测试
↓
回归检查
↓
Lint
↓
TypeCheck
↓
Build
↓
Dist
↓
必要的人工验收
↓
Commit
↓
稳定版本按需创建 Tag
```

不要因为下一版本“看起来很简单”，就在当前任务中顺手实现。

宁可：

> 小版本完整、稳定、可验收

也不要：

> 大版本功能很多但只有一半可靠。
